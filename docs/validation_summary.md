# ExperimentLab validation summary

This note describes how the generated baseline, analysis pipeline, and isolated
scenario fixtures handle the required validation cases. The negative scenarios are
metadata in `data/ground_truth/anomaly_scenarios.json`; they are not inserted into
the clean baseline database.

## Baseline and ground truth

The generator creates ten experiments with 5,000 assigned members each. Baseline
assignments satisfy the one-assignment-per-member-per-experiment constraint, and
event foreign keys and event ordering are checked by SQLite. Synthetic truth labels
are stored separately in `data/ground_truth/ground_truth.json`. They are for
validation only and are not analysis inputs or exported as part of the clean
analytical dataset.

## Labelled negative scenarios

| Scenario | Fixture representation | Baseline handling |
|---|---|---|
| `multiple_variant_assignments` | Identifies an existing assignment and an attempted assignment of that member to the alternate variant. | Not inserted. The schema's unique `(experiment_id, audience_member_id)` constraint and deterministic assignment primary key reject it. |
| `exposure_before_assignment` | Contains an exposure timestamp one minute before the referenced assignment. | Not inserted. The database trigger rejects exposure events earlier than assignment. |
| `inconsistent_outcome_window` | Records a 14-day fixture analysis window against a metric definition with a seven-day attribution window. | Not inserted. The analyzer uses the immutable metric definition's attribution window when including outcomes. |
| `ignored_sample_ratio_mismatch` | Supplies an illustrative 3,500/1,500 observed split against a planned 50/50 allocation and labels the warning as ignored. | Not inserted. SRM is computed from baseline assignment counts and saved as a diagnostic on each result. A significant SRM is a warning, not an automatic analysis failure or an exclusion rule. |
| `metric_definition_changed_after_results` | Describes a result snapshot tied to version 1 and a later version 2 with a changed window. | Fixture metadata only. Metric-definition versions and results are immutable; the later definition is a new version, and existing results remain linked to the earlier definition/version. No result or version-2 row is generated by Phase 3. |

These are fixture descriptions for inspection and validation, not a harness that
executes each intentionally invalid write against the baseline database.

## SRM behavior

The analysis pipeline applies a chi-square goodness-of-fit test to observed
assignment counts and planned allocation probabilities. A p-value below `0.001`
sets SRM status to `warning`; otherwise it is `pass`. The diagnostic is stored with
the result and does not change the intention-to-treat population, discard users, or
turn the SRM warning into an automatic failure.

## Guardrail behavior

For each enabled guardrail, the analyzer calculates control and treatment outcomes
over the metric definition's attribution window. It computes regression in the
configured direction and compares the point-estimate regression with `max_regression`.
A regression beyond the threshold is a warning for `warning`/`info` severity and a
failure for `blocker` severity. Guardrail check details are retained in the result's
analysis configuration JSON. The implemented threshold check is not a separate
significance test.

## Reproducibility and persisted results

Each persisted result records its analysis-plan version, metric-definition ID and
version, outcome-window boundaries, SRM and guardrail statuses, and a SHA-256 hash
of the input snapshot. Results append to the immutable `experiment_results` table;
they are not overwritten. Re-running analysis therefore creates another result
snapshot.
